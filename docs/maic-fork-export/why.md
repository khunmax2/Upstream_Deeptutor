09766e6b7  2026-09-07  khunmax2
Play speech responses that arrive as raw PCM

`/v1/audio/speech` does not oblige a provider to return a container, and several
OpenAI-compatible servers answer `audio/L16` — bare PCM16 samples, no header.
`getAudioResponseFormat` does not recognise those media types and falls through
to its `mp3` default, so the bytes reach the browser labelled as MP3. Every
consumer then fails identically, because `new Audio(URL.createObjectURL(blob))`
cannot decode them:

    TTS test failed: Failed to load because no supported source was found.

which is the browser's own message and says nothing about the cause. Measured
against such a server: `content-type: audio/L16;rate=24000;channels=1`, and the
first bytes carry neither a RIFF nor an ID3 magic.

`decodeAudioResponse` adds the missing step. It parses the media type for
`audio/l16`, `audio/pcm` and `audio/x-pcm` — taking `rate` and `channels` from
its parameters, defaulting to 24 kHz mono when absent — and prepends the 44-byte
RIFF/WAVE header that makes the same samples playable. Anything already in a
container is returned untouched.

**Byte order is measured, not assumed.** RFC 2586 defines `audio/L16` as
big-endian and `audio/pcm` as little, and real gateways disagree with the spec
often enough that either default produces noise on the other half of them — the
server this was first tested against sends little-endian under an `audio/L16`
label. So for L16 the samples are read both ways and the smoother reading wins:
speech is a continuous waveform, and the wrong byte order swaps each sample's
high and low halves, turning every step into a jump. On that server the two
readings differed by a factor of thirteen. Silence and clips too short to measure
fall back to the specification, and `TTS_L16_BYTE_ORDER` forces the choice for a
gateway that is known. `audio/pcm` is little-endian by definition and skips the
measurement entirely.

Done at the single point the three provider paths converge on (OpenAI, Lemonade,
VoxCPM had identical five-line endings), so preview, regeneration and classroom
playback are fixed together and the rule stays in one place: everything past this
function is in a container, little-endian.

Verified two ways: ten unit tests over the header fields, the media-type
parameters, both byte orders, the short-clip and silence fallbacks and the
pass-through cases; and a real 16,384-byte response from such a server, whose
byte order the detector reads correctly and whose output an independent decoder
opens — Python's `wave` module reports 1 channel, 16-bit, 24 kHz, 8,192 frames.

basePath is not enough on its own. It prefixes <Link>, the router and /_next/
assets; it does not touch a URL the app writes itself, and this app writes 74
fetch('/api/...') calls across 44 files plus three EventSource streams. Under a
prefix every one of them leaves for the root of the host.

A reverse proxy would normally absorb that, but this host already serves
/sansarnnews, /research-helper, /dol, /deepwitya, /opdc-assistant and

rule there would sit in front of all of them. So the app prefixes its own URLs.
Rewriting 44 files would be 44 files to re-apply on every subtree pull;
rewriting the two globals they funnel through is one, and it is inert when

wrapping only fetch would have left it silently dead. For /public, three choke
